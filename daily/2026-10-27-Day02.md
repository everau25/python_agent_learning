## 今天学了什么（原记录，2026-10-27 晚）

### 1. Coze 工作流
把一个任务拆成按顺序执行的节点：开始 → 处理（大模型 / 代码 / 插件等）→ 结束。
关键是输入输出要对得上：上一个节点的输出，就是下一个节点的输入，工作流就是把“一步想不明白的大任务”变成“一步步能跑通的小步骤”。

### 2. 数据库
给智能体一个能记住东西的地方，不再是聊完就忘。
核心是先定表结构再写数据：字段是什么、什么类型、哪张表存什么，定清楚了，工作流里的读写节点才不会乱。
今天实战里用到的就是这个思路：档案、计划、打卡分开存，用 user_id 串起来。

### 3. AI 智能体的构建
智能体不只是一个会聊天的模型，完整的一套是：
人设与提示词（它是谁、按什么规则办事）+ 工作流（它按什么步骤做事）+ 数据库 / 知识库（它记得什么、查什么）。
提示词里要写死硬约束（比如不该出现什么、数字不许编），否则模型会自己“自由发挥”。

### 1. 多模态插件（进阶，Day01 已讲过的部分这里只记新点）

多模态的定义，思维导图里写得很清楚：模型在处理数据的时候，不仅仅可以针对文本数据，同样还可以处理视频、音频、图像；输出的时候也不仅仅是文本，同样也可以是视频、音频、图像，这样的模型就叫多模态模型。

应用场景和 Day01 一样：文案（基于产品介绍和 LLM，生成风格化的文案，比如小红书文案）、商品图片（文生图、图生图，生成商品图，还可结合图像编辑模型一件替换模特衣服、首饰等，节省模特成本）、广告语音（基于文案生成广告配音）、广告视频（基于文案、商品图片等生成广告视频，节省广告拍摄成本）。

Day02 新讲的点，主要是文生图的参数说明，其他图像、音频、视频的用法和 Day01 相同：

- **图像处理**：文生图（通过文本内容要求生成符合题意的图片）、图像画质提升（对比较模糊或质量比较低的图像，提升为较为清晰或质量比较高的图像）。
  - 文生图工作流设计：在流水线中添加图像生成节点，选择模型、设置好分辨率等信息。Day02 补充了一个参数说明：`req_schedule_conf` 是模型调度策略或风格优化器，其中 `general_v20_9B_pe` 是基础模型版本标识或提示词增强配置，用于指定调用具体的文生图模型内核（如 general_v2.0 系列），确保生成图像符合基础的质量标准和语义理解能力；`general_v20_9B_rephraser` 是文案重写与美感优化模块，主要作用是对用户输入的原始提示词进行语义润色和风格重构，以提升生成图像的美感和图文匹配度，当需要生成更具艺术感或构图更精准的图片时用它。
  - 好的图片提示词还是那套：主体 + 场景 + 风格 + 光线 + 构图 + 细节。老师例子：金毛犬雪地玩耍图、金毛犬公交车站下小雨图。

  - 语音识别（ASR）：把声音转成文字，大模型负责把文字整理好。插件商店里搜“语音识别”，分小模型版和大模型版，区别在识别准确率和资费上。工作流里加“语音识别”节点，试运行上传素材 06-音频片段.MP3，输出了素材中的内容，文字识别都是对的，但没有标点符号，可以在语音识别节点后追加一个 LLM 节点做输出润色。课堂练习（8 分钟，已完成）：把 06-音频片段.MP3 转换成文字。

### 2. 工作流中的循环结构（Day02 新内容）

思维导图里的一句话：重复的时候多做几次，就是循环。

**案例：小红书电商营销文案批量生成工作流**

输入内容：请帮我生成始祖鸟 Alpha SV 冲锋衣、凯乐石 Mont-X 冲锋衣、拓路者雪鹰 2.0 冲锋衣的文案。

流程是：

1. 用户输入一个自然语言语句，描述要生成哪些主体的营销文案。
2. 用大模型提取主题，并生成数组格式返回。提示词是：你是一个小红书电商文案批量生成工作流主体提取助手，能够根据用户输入的内容提取出来里面包含的主体，并以数组格式返回。
3. 通过循环结构对每个主题逐个处理：基于 LLM + 联网搜索功能生成对应主体的文案。首先设置循环节点，循环体中设置大模型的输入与输出，这里输入需要选择 `item(in topics)`，也就是循环当前正在处理的那一个主题。
4. 循环体里大模型的提示词是：你是一个小红书文案生成专家，能够根据用户输入的主题进行互联网检索，并生成小红书文风的爆款文案，作为软广内容，提升产品销售的转化率。注意：文案不少于 500 个字；文案需要严格按照小红书的文风输出。
5. 试运行流水线，输入上面那句冲锋衣文案，循环体执行结果是：根据输入的 3 个主题，生成了 3 个对应的内容。最终预览的文案遵从了小红书常见的文风。

关键理解：循环不是把 3 个主题一次性丢给大模型写一段，而是先拆成数组，再一个一个过循环体，每个 `item` 单独生成一次，最后汇总成 3 份文案。拆分 + 循环 + 逐个处理，这三步缺一不可。

**课堂练习（8 分钟，已完成）：批量生成 AI 岗位介绍**

用户一次输入多个岗位名称，工作流需要自动拆分岗位，并逐个生成岗位介绍。例如：请帮我介绍一下 AI 大模型开发工程师、NLP 算法工程师、Agent 应用开发工程师。

- 大模型提示词（提取岗位）：你是一个岗位名称提取助手。请从用户输入中提取所有岗位名称，并以 JSON 数组格式返回。要求：只返回岗位名称数组；不要输出解释；不要输出多余内容；如果没有识别到岗位名称，请返回空数组 `[]`。示例输出：`["岗位1", "岗位2", "岗位3"]`。
- 循环体中生成岗位介绍的提示词：你是一个 AI 大模型就业指导老师。请根据当前岗位名称，生成一份适合零基础学生理解的岗位介绍。要求：先用一句话说明这个岗位是做什么的；说明该岗位的主要工作内容；说明需要掌握的核心技能；说明适合什么类型的学生学习；最后给出一条学习建议；表达要通俗易懂，不要堆砌术语。当前岗位：`{{item}}`。

### 3. Multi-Agent 多智能体（Day02 新内容）

**3.1 为什么需要多智能体**

在单 Agent 模式下，所有任务都交给一个智能体处理。如果任务越来越多，智能体就会变得越来越复杂：

```
一个 Agent
  ├── 处理旅游规划
  ├── 处理文档读取
  ├── 处理翻译
  ├── 处理知识库问答
  ├── 处理数据库查询
  └── 处理用户闲聊
```

这样会带来一个问题：一个智能体什么都管，提示词会越来越长，调试会越来越难。

为了解决这个问题，Coze 提供了多 Agent 模式（也就是 multi-agent），该模式下可以为智能体添加多个 Agent，并连接、配置各个 Agent 节点，通过多节点之间的分工协作来高效解决复杂的用户任务。这就是一个经典的主从模式或者父子模式的多 Agent 结构。

思维导图里的拆分说法和上面一致：父子结构，由父 Agent 负责任务的分发操作，由子 Agent 负责具体的任务执行。

**3.2 案例：多语言翻译多智能体**

业务逻辑：输入一段文本，并指定要翻译的目标语言，智能体最终返回用户要求的目标语言的译文，支持中文、韩语、日语三种（老师笔记里原文写的是“中文、汉语、日语”，结合后面的父子拆分和调试用例，应为中文、日语、韩语三种）。

案例业务逻辑比较简单，单 LLM + 提示词即可实现较好效果，达不到需要使用 multi-agent 的场景。这里不必纠结，目的是基于这个案例，学会如何使用 multi-agent 功能。

拆分方式是父子结构：

- 父 Agent：分发翻译任务，将用户输入翻译为目标语言。
- 中文 Agent：如果目标语言是中文，则调用此 Agent 实现翻译。
- 韩语 Agent：如果目标语言是韩语，则调用此 Agent 实现翻译。
- 日语 Agent：如果目标语言是日语，则调用此 Agent 实现翻译。

**创建一个 Multi-Agent 智能体**

首先创建一个智能体，命名和介绍后，需要切换到多 Agents 模式。多 Agent 的执行过程有点类似于工作流，接下来查看多 Agents 模式下支持哪些节点类型，添加“添加节点”，分为以下 3 类节点：

1. Agent：Agent 节点是可以独立执行任务的智能实体。默认情况下，智能体内添加了使用智能体名称的 Agent。功能相对比较简单，仅支持提示词和技能两个功能。没法实现类似工作流的功能，较难实现比较复杂的业务流程，因此更适合用在对话类的业务上。
2. 工作空间智能体：将已发布的、可以执行特定任务的单 Agent 智能体添加为节点。可以把已经集成了各类插件、业务逻辑的复杂工作流的智能体作为其中一个 Agent。在实际工作中，需要使用到多 Agents 的时候往往是功能非常复杂的时候，将已经发布到工作空间的多个复杂功能 Agent 结合一个父 Agent 做路由，往往是更常见的做法。
3. 全局跳转条件：适用于所有 Agent 的全局条件。只要用户输入满足该节点的条件，则会立即跳转到 Agent。用于实现复杂 Agent 的流程控制。

**父 Agent 和子 Agent 的提示词（老师笔记里给出的部分）**

父 Agent 适用场景：当用户输入一段需要翻译的文本，并指定目标语言时，调用该 Agent 判断用户要翻译成哪种语言，并将任务分发给对应的翻译 Agent。

父 Agent 提示词，重点负责“判断 + 分发”，不负责具体翻译：

```
你是一个翻译任务分发助手。

你的任务是根据用户输入，判断用户希望将内容翻译成哪种目标语言，并调用对应的翻译 Agent。

分发规则：
1. 如果用户要求翻译成中文，调用“翻译为中文”Agent。
2. 如果用户要求翻译成日语，调用“翻译为日语”Agent。
3. 如果用户要求翻译成韩语，调用“翻译为韩语”Agent。
4. 如果用户没有说明目标语言，请先询问用户希望翻译成哪种语言。
5. 你只负责判断和分发任务，不需要自己完成翻译。
```

子 Agent：翻译为中文，适用场景是当用户希望将输入内容翻译成中文时，调用该 Agent。提示词：

```
你是一个中文翻译助手。

你的任务是将用户输入的内容翻译成自然、准确、通顺的中文。

要求：
1. 只输出中文译文。
2. 不要输出解释。
3. 不要添加无关内容。
4. 如果原文中有专有名词，请尽量保留其准确含义。
```

调试 Agent，输入以下内容：

```
"Good morning" in Chinese
"Good morning" in Japanese
"Good morning" in Korean
```

**课堂练习（8 分钟，已完成）：设计一个多语言翻译 Multi-Agent**

本练习要完成一个多语言翻译智能体。用户输入一段文本，并说明要翻译成哪种语言，系统需要自动判断目标语言，并调用对应的翻译 Agent。

一句话理解：父 Agent 负责判断要翻译成哪种语言，子 Agent 负责完成具体翻译。

请创建一个 Multi-Agent 智能体，支持以下 3 种翻译能力：翻译为中文、翻译为日语、翻译为韩语。

### 4. 发布智能体（只在老师笔记里有，思维导图里没有这一节）

点击项目开发，找到发布的智能体，点击进入后，再地址栏上复制 id。

今天搭建的另一个智能体，配套搭建文档已单独存在 `workspace/coze-diet-planner/`，这里只记结构，不重复贴全文：

- **Bot 人设**：专业、亲切的营养师口吻，先建档再出计划，数字必须基于档案和食物营养库算，不编造。
- **数据库（3 张表）**：
  - `user_profile`：性别、年龄、身高、体重、目标（减脂 / 增肌 / 保持）、活动量、忌口过敏、口味、预算、每日热量与三大营养素目标
  - `meal_plan`：按日期 × 餐次（早餐 / 午餐 / 晚餐 / 加餐）存菜名、份量（克）、热量、蛋白质 / 碳水 / 脂肪
  - `checkin`：饮食打卡与体重记录，含日期、内容、热量、完成度
- **工作流（3 条）**：
  1. 建档与热量计算：输入档案 → 代码节点算 BMI、BMR（Mifflin-St Jeor）、TDEE、热量与三大营养素 → 写入 `user_profile`
  2. 生成饮食计划：读档案 → 检索食物营养知识库 → 大模型生成 7 天计划（JSON）→ 确认后写入 `meal_plan`
  3. 饮食打卡：输入吃了什么 → 知识库估算热量 → 读当日目标 → 写入 `checkin`，汇报已摄入 / 目标 / 剩余
- **每周复盘**：每周日定时触发，按打卡天数和体重变化调下周热量目标（例如打卡 ≥5 天但体重两周不动，下周热量减 5%），并一句话说明改了什么、为什么。
- **知识库**：食物营养库（每 100 克可食部的热量与三大营养素约数），供生成计划和打卡估算时检索。
- **发布原则**：先在扣子内预览测试建档 → 出计划 → 打卡全流程，不公开发布到 Bot 商店，个人使用即可。

## 今天的核心理解（一句话）

智能体 = 提示词定规矩，工作流定步骤，数据库定记忆，知识库定依据——四个拼起来，才能从“能聊天”变成“能办事”。Day02 再往上加了一层：如果一个智能体什么都管，提示词会越来越长、调试越来越难，那就拆成父子多智能体，父 Agent 只管分发，子 Agent 各管一件事；如果一件事要重复做很多遍，就不要一个一个手动跑，用循环结构先拆成数组，再逐个处理。
